# 片段提示词注入系统

插件内置提示词注入不再使用完整提示词文件，而是定义提示词片段。这些片段会在前文没有注入或发生改变的情况下按顺序注入，以提供充足信息并节省上下文。

## 片段的定义

一个提示词片段包含以下信息：

- namespace: (string) 提示词片段所属命名空间，本插件本身的命名空间为 `whale-craft`
- name: (string | undefined) 提示词片段名称。
- content: (string) 提示词片段内容。为 Markdown，一般以 `##` 级标题开始
- previous?: 前驱，若指定，则只在上文中找到对应前驱且本提示词未注入时进行注入
  - namespace: (string) 前驱所属的命名空间。
  - hash: (string) 前驱的哈希

> 这两处命名空间按理应当只允许填入本附属插件所申请的命名空间，但是现在还没有命名空间系统和附属插件系统，所以都允许。!!TODO!!

简洁起见，开发文档中定义提示词片段会在开头使用 yaml 块标注相关元数据。这些块不进入提示词。一般这样标注：

```yaml
name: whale-craft:meta #namespace:name，不定义直接省略
previous: whale-craft:xxx #namespace:hash，不定义直接省略
```

名称应当是小写连字符，可以不定义。只是给助理展示和提及用，无特殊功用。

前驱的设计，是为了面对一些“提示词需要销毁的情况”。比如之前的提示词包含“这个版本的 move 尚不成熟”，但是后来成熟了，就可以专门定义一个提示词片段说“move 工具成熟了”，以前面的提示词为前驱。如果从来就没有注入过前面的，则这个补丁提示词也不用注入。

## 注入时机

片段提示词注入发生在玩家手动发起对话后。这时，应当先检查目前环境快照是否较对话的发生变化（查找环境快照逻辑见下文。或者之前不存在任何提示词注入），如果没有，则跳过注入。如果是，再收集可见上下文中注入过所有提示词的命名空间和哈希，执行注入逻辑。

在压缩上下文后，也触发一次注入，来补投提示词。注入逻辑与前文相同，只是在这种情况下实际表现为“没有前驱的全部注入，有前驱的全部不注入”。可以据此优化。

所有哈希一律为将 UTF-8 原文使用 SHA-256 哈希得到小写 hex 字符串。提示词注入的哈希源数据为实际会拼接进正文的提示词片段正文。

### 环境快照

环境快照收集插件运行时的环境，来判断提示词片段是否已可能发生变化，是否需要执行注入逻辑。

环境快照收集的信息有，宿主版本、插件版本、附属插件及其版本（将来计划），将其序列化为 json，对象键和数组均按字典排序，再进行哈希以储存。

从对话中读取环境快照，逻辑为倒序寻找最近的上下文片段注入日志，使用其环境快照。

## 提示词注入

一次提示词注入，会一次性注入所有本次所需注入的片段，结构如下。

```markdown
# 片段提示词注入

<prompt-segment name="whale-craft:meta">
## 片段提示词概述

...
</prompt-segment>

...
```

每个片段提示词使用 `prompt-segment` 标签包裹，标签属性中用 `name` 指定片段的命名空间和名字。未定义名字者，使用 `命名空间:`，如 `whale-craft:`。

如果提示词正文含有 `<prompt-segment>` 或 `</prompt-segment>` 及类似标签结构，应当将尖括号转义。其余情况无须转义。

### 元数据

在对话日志中保存元数据，以记录注入的元数据。这些元数据不会进入 LLM 上下文，只作检索用。（参见环境快照与提示词注入时机。）

元数据存在对话日志对应条的 `source` 下。

- env: (string) 环境快照哈希
- type: "prompt-segment"
- version: 1
- segments: (object[]) 本次注入的提示词片段元数据
  - name: (string) 命名空间和名字，中间用冒号分隔。未定义名字者，使用 `命名空间:`。目前只有命名空间在查找时有使用价值
  - hash: (string) 提示词正文的哈希
