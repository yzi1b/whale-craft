# 全方位可扩展可配置可复用灵活注意自合并自适应可追溯看门狗

*前不见古人，后不见来者。念天地之悠悠，独闭门而造车。*

## 特性

- 全方位：尽力实现所有必要的事件的监听
- 可扩展：其他插件可以注册更多事件（长远计划，先预留）
- 可配置：助理可以配置各触发器的参数
- 可复用：配置可储存，可复用
- 灵活注意：可将配置作为注意项目叠加
- 自合并：某些连串事件，自动延迟提醒助理，合并多次可能唤醒
- 自适应：自动适应连串事件的节奏，比如玩家说话习惯，优化提醒频率（这一项是大饼）
- 可追溯：事件记入队列，助理可以查阅和留档

## 基础设定

### 可观测事件

*全方位*

可观测事件，分为事件事实和事件修饰。前者直接反映游戏中发生的一个事件，后者在前者出现后对前者进行条件判断，满足条件后加以修饰，标记一个事件满足了一个条件。

事件事实可被配置是否记录、是否提醒。如果事件事实本身不被记录、不被提醒，可被事件修饰按照其自身配置标记为记录、提醒。

事件列表，见 [events.md](events.md)。

### 事件处理流程

*自合并、自适应*

在观测的一个事件发生后，会立即将其记录。按照 record、wake 配置决定是否记录，唤醒。为 true 则已决定记录、唤醒，为 false 则取决于后面的逻辑。无论如何，后面的逻辑固定执行。

随后检查该事件的每个事件修饰的逻辑，判断每个事件修饰是否命中。检查可能是串行的，可能是并发的，任何检查不能依靠修饰之间的先后顺序，且检查应当是能在1s之内完成的，超出则认为未命中，计入看门狗异常日志。检查后，符合的修饰将被附加到事件中，同时对事件进行“扩充”，如果其 record、wake 配置为 true，则将事件转变为记录、唤醒。如果为 false，则保持事件原来状态。唤醒必定记录。

为了合并多次重复唤醒，特加入可配置的延迟 delay。delay 必须大于等于 0，0 为不延迟。delay 决定事件发生后延迟多长时间再实际通知助理，等待期如果有其他事件先结束等待，则直接通知。还在延迟的事件也记为已通知，因为都在一个事件队列中。事件修饰的 delay 可设为小于 0，意为不改变原始状态。若大于零，则将实际延迟设为二者中的更小值。多个修饰叠加，实际为最小者。

唤醒助理时，注入的提示词中，指明实际触发的事件对象。如果还有多个仍在延迟但同时被视为已唤醒的事件，则会告知计数。始终要求助理检查事件列表。

### 配置层次

*可配置、灵活注意*

```text
基础配置 <--覆盖-- 场景配置 <--扩展-- 注意配置*n
```

基础配置作为看门狗的最低级配置，控制一切的默认行为。在没有场景配置和注意配置时，保证必要事件的送达。基础配置始终是完整的。

因为生存、创造、小游戏等不同语境，所需要观测的事件不同，给以场景配置。场景配置直接覆盖基础配置，即冲突的项直接以场景配置为准。场景配置不需要完整，因为有基础配置兜底。

因为即使在统一语境，比如生存，挖矿、种田、打怪所需要观测的事件仍有不同，给以注意配置。注意配置可以生效多个，共同扩展前两项配置。注意配置有敏感、钝感可配置。出现冲突的项时，按配置以更敏感的或更钝感的为准。多个注意配置相互冲突，以更敏感的为准。注意配置不需要完整，它只是在已有配置上的扩展。

### 队列模型

*可追溯*

事件队列在一次连接开始时构造，在一次连接断开后销毁。

事件队列的每一个元素是一个事件对象，其结构如下：

- timestamp: (number) 事件记录的时间戳。
- name: (string) 事件的注册名。
- content: (object) 事件的载荷。
- modifiers: (Record<string, object | true>[]) 命中的事件修饰符及其载荷。键为修饰符注册名，值为载荷，无载荷则为 true。

事件队列在AI读取时会进行处理，实际交给AI的是一份修改过的副本。timestamp 字段会被替换为 time，为字符串，值为本地化处理的可读日期时间。修饰符会做精简，同种事件事实所携带的同类型相同载荷的修饰符，将只保留最先出现的。

助理读取事件列表，可选择读取数量（可预先查看事件总量），或全部读取。读取时可以选择是否消费，即读取后从事件列表中移除已读部分，默认消费。读取结果可以直接反应到上下文中，可以落盘。

### 配置持久化

*可复用*

配置是一个 Record<string, object>。键为事件的注册名，值的结构如下：

- xxx: (xx) 一个配置项。
- modifiers: (Record<string, object>) 事件修饰符及其配置。键为注册名，值为配置。

因此，一个事件的配置项中绝对不能直接有 `modifiers` 这样的键名。

如配置聊天（节选）：

```json
{
  "message.chat": {
    "includeSelf": true,
    "treatSystemAsChat": true,
    "record": true,
    "wake": false,
    "delay": 10000,
    "modifiers": {
      "mention": {
        "keywords": ["deepseek", "ds", "harness", "whale", "ai", "agent"],
        "players": [],
        "record": true,
        "wake": true,
        "delay": -1
      },
      "nearby": {
        "distance": 32,
        "players": [],
        "record": true,
        "wake": true,
        "delay": -1
      }
    }
  }
}
```

AI可将配置导出导入。其中“场景配置”后缀名为 `.scene.wcwc.json`，“注意配置”后缀名为 `.focus.wcwc.json`。其中，“wcwc”是“Whale Craft Watchdog Config”的缩写，而不是对这套系统过于精妙而“卧槽卧槽”的感叹。

AI导出的配置，其json中还有额外的元数据。

其中，场景配置：

```json
{
  "wcwc": 1,
  "type": "scene",
  "config": {}
}
```

config 中存储的就是实际的配置。wcwc 字段表明版本号，目前为 1。

注意配置：

```json
{
  "wcwc": 1,
  "type": "focus",
  "sensitive": true,
  "config": {}
}
```

sensitive 为 true，则视为敏感，否则为钝感。

基础配置存储在 dsh 配置目录中，不得导入导出。

```json
{
  "wcwc": 1,
  "type": "base",
  "config": {}
}
```

此外，内存中三种配置如何存储不由此文档界定。AI 如何传入、保存配置或临时指定配置，获取配置，详见文具文档。
